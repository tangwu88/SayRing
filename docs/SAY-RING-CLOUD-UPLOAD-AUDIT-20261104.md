# 测量记录与服务器上报只读核验

日期：2026-11-04。用户在 R7 Ultra 真机排查期间要求检查测量数据上报服务器的情况。范围为当前已授权 **iPhone XR／Say Ring 1.0.10（1235）测试账号** 的本地数据库、实际服务器查询和客户端上传规则；没有主动补传健康数据、扩大上传范围、切换账号或修改服务器。

## 实查结果

当前账号本地共98条记录，32条已标记同步、66条待同步。读取正式 API 返回 HTTP200，一页32条，分页已结束。逐条按原记录ID对账：**32/32均存在于服务器，指标、手机保存的显示数值、原始时间均匹配**；时间以服务端毫秒精度核对，没有大于1毫秒的差异。没有仅凭按钮恢复或本地 `synced=1` 推断云端成功。

## 上报目标与实际规则

- 实际客户端为 `GlobalSaydianApiClient` 的 `GlobalHealthApi`：上报到 **`https://app.saydian.cn/global/api/saydian-app/v2/health/records/batch`**；本次只读核验使用同一通道的 `GET .../health/records?product=say-ring&platform=ios`。
- 不能用父类旧小程序 `jrjk`／`daily-date` 接口解释此客户端；global mixin 已覆盖逐条V2上传。不要把 `/global` 数据通道与别的部署、后台或账号混作一份数据。
- `AppController.production` 为iOS创建的 `HealthSyncService` 和API上传策略，固定只允许**活动与睡眠**。本轮读取运行中策略也确认此边界，没有读卡片远端授权能扩大上传的入口。
- 因此上述66条心率、血氧、皮温、HRV保留在本地待同步，属于当前iOS上传范围，不是已证实的服务器丢失或上传网络失败。后台当前允许显示这些指标，只控制读取／展示，不会自动开放上报。
- 每批最多10条；客户端逐条验证来源、数值与时间，只按服务端 `acceptedIds` 更新同步标记。未确认、被拒绝和不在发布范围内的记录不会假记成功；未来／无效历史走隔离，不能随意改回待上传。
- 服务端实现以用户身份为所有者，校验幂等键、逐条返回接收／拒绝，并在事务中保存记录与回执。本次没有发送新的批量POST来测试写入；结论来自现有真实数据对账与源码契约，不能冒充新写入压测。

## 验证方法与隐私

通过已核对的本机App进程读取原账号和数据库所有者，只读打开私有加密容器副本。数据库密钥、Bearer、记录ID和健康数值仅在检查进程内用于对账，不写入报告或Git。实际健康查询都是GET；原会话的正常读取／必要续期与健康上传分开，不能声称整个App后台期间完全没有网络活动。

私有结果在 `build/coolwear-readonly-1235-20261104/xr2/cloud-upload-audit/`：`report.json`、`comparison-report.json`及加密备份。报告仅保留计数、校验结果和必要来源元数据。开始SDK修复前的136条记录，在本次142条全owner快照中全部保留，原payload与原始日期均未改变。

## 本轮结论的边界

1. 已有活动／睡眠的云端记录及全部32条本机已同步记录，对账通过；没有发现这32条被服务器丢弃。
2. 当前iOS的66条生理记录不会因点戒指同步自动上云；本次没有修改此范围。
3. R7 Ultra本次有效HRV仍未验收，不能把历史HRV、配置／能力尚未就绪时的启动拒绝、命令ACK或超时回到ready当成有效测量。两次自动测试启动的拒绝分别属于发布配置／设备能力门禁，不是两次原生180秒测量；不绕过门禁。
4. 这次实查为XR当前账号。华为PPA-LX3使用另一个账号，不能拿XR的32条对账结果替它作服务器验收，也不为只读审计重新启动华为去触发自动补传。
