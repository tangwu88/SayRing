## RECHECK-01：旧恢复异常不能清掉新的正常连接

**触发条件：** 自动恢复已开始，持久状态清理等异步操作尚未结束；期间换设备、换账号、退出或销毁控制器；旧操作随后抛出 PlatformException 或一般异常。

**旧行为：** `_restoreReconnectedDevice` 的成功路径校验代次，异常分支却无条件清空当前设备/能力并切换到 error，覆盖新的正常连接。

**修复：** 两个异常分支在任何状态修改前共同检查销毁、账号转换、恢复暂停/授权、登录代次、同步代次、稳定 owner 和当前目标。过期异常直接结束；当前操作确实失败仍清理当前失效连接并报告错误，不能吞掉全部故障。

**真实断言：** 两类异常分别验证新目标 ready 与能力不变、退出后仍 disconnected、另一账号连接不变、销毁后不通知，以及当前任务失败仍为 error。测试先建立并断言新状态，再释放旧失败 Future，避免只测试假设中的代次值。

## RECHECK-02：首次请求未提交，恢复登录后能按原操作重试

**触发条件：** 首次确认前本机已持久 `decisionUnknown`，但凭证失效、认证拒绝或网络异常发生在服务端写入前，精确目标绑定尚不存在。

**旧行为：** 后续只读“更早其他绑定”证明要求先存在目标行，固定返回 false；重新登录与反复点同步都不能推进。

**修复：** 新首次请求先在精确 owner/target 的安全存储中持久化 UUID v4 操作编号，再提交携带同编号的首次绑定请求。待确认时查询原编号的回执：

| 明确回执 | 客户端动作 |
| --- | --- |
| `preserve` | 原决定为保留数据；清理当前未知保护并沿原同步流程读取，不发送清空 |
| `not-found` | 原操作尚未记录；仅按同一 owner、target、operationId 重试，不生成新编号 |
| `clear-issued` | 授权已发出，继续保留保护，不重发清空、不当作初始化完成 |
| 401、404、超时、格式或归属不符 | 保留待确认和现有数据；不能把接口错误当 `not-found` |

新 API 分支必须 `return await` 首次请求，使真正异步异常进入已有 catch，保持工作中的蓝牙 ready，而不是把账号/网络错误变为蓝牙 error。普通连接元数据补报不是新的清空授权。

**真实断言：** 401、404 和网络超时均在 fake 中通过异步 Future 抛出；失败后连接、ready、真实能力和可重试状态保留。恢复只读请求后先获得 `not-found`，再以完全相同的操作编号/owner/目标提交并得到 preserve；只有 1 次历史读取、0 次清空、0 次额外重连。这里验证的是控制器协议流程，不代表真实手机登录或线上服务已经验收。

## RECHECK-03：同一枚旧 R8 的原决定可追溯

**触发条件：** 老会员换手机或本机没有记忆绑定，重新连接唯一的一枚旧 R8；服务端决定不清空，但返回包丢失。该会员没有“另一条更早绑定”可供旧证明使用。

**修复：** 新请求依精确 owner、target 和持久操作编号查询原决定。`preserve` 回执直接确认原决定，不重新 POST 首次绑定、不重新申请清空；操作编号和状态在一个安全存储值中保存，状态迁移保留编号，完成时一并清理。

**真实断言：** 首次决定已记录为 preserve、响应丢失后，控制器用原编号 GET 恢复；首次决定 POST 仍只有 1 次，未走旧首次接口或旧其他绑定证明，清空 0 次。重建控制器后仍使用原编号。同一旧目标不需要在测试中预造“另一条绑定”来假装通过。

**必须保留的旧版本边界：** 旧版枚举状态没有操作编号，服务端历史事件也未必保存可追溯的原决定。客户端不得为旧 `decisionUnknown` 补造新编号，不得因现在有绑定、重复提交返回 false 或当前请求 401 就倒推旧决定。仍只接受原有严格的更早绑定证明；证明不足时继续保护。后续如需人工恢复此类遗留状态，必须单独取得可信归属和原决定证据，不能在本轮自动绕过。

## RECHECK-04：CoolWear 真实 ACK 后完成一次保绑定新握手

**触发条件：** 新会员首次初始化真正收到 CoolWear 历史清空 ACK，并成功持久为 `historyClearAcknowledged`；蓝牙仍保持连接，新握手尚未完成。

**旧行为：** 同步受保护，已连接又没有重连入口；旧测试人为调用 disconnect/connect 掩盖了用户流程死路。

**修复：** 仅在明确 ACK 和持久化成功后异步安排一次现有保绑定重连。不能在当前连接函数内部 await 此 helper，否则 helper 等当前连接槽会互相等待。新握手完成后按原规则解除 ACK 状态并恢复手动同步。未确认命令、ACK 存储失败、迟到 ACK、账号/目标变更均不触发新的自动操作；绝不重复清空。

**真实断言：** 从首次连接开始不由测试补调用 disconnect/connect，生产流程自行产生总计 2 次连接和 1 次普通断开、0 次 forget、1 次 clear、1 次首次决定。随后真实 DevicePage 的同步按钮可用，已连接不显示误导重连；手动同步前历史读取仍为 0，点击后为 1。对 requested/factoryResetRequested、持久失败、迟到 ACK、换目标及退出另设反例。

## 影响文件与防复发约束

- `lib/services/app_controller.dart`：异步异常归属检查、首次初始化共用流程、操作回执恢复、明确 ACK 后的一次新握手。

- 后续现场追加 `lib/ui/pages/devices.dart` / `app_controller.dart` 搜索竞态门禁，以及 `wearable_routing.dart`、Android `CoolWearRingBridge.java` / `CoolWearRecoveryTarget.java` 的失活通道退出；精确证据、回归和未验边界见本文件后续补记。

固定规则：

1. BLE 连通、能力支持、身份有效、首次决定、原生执行回执分别判断，不复用一个 pending 布尔代替全部事实。
2. 成功和失败回包使用相同的 owner/target/代次边界；过期错误和过期成功同样不能修改新会话。
3. 异步 try/catch 内返回远端 Future 时检查是否需要 await，不以同步 throw 的假测试替代真实异步失败。
4. `not-found` 是经过认证和精确匹配的业务状态，404/401/超时不是 `not-found`。
5. 可重试的是同编号的原决定；可能已执行的物理 clear/reset 从不自动重放。
6. 操作编号持久失败时不提交；清空尝试状态持久失败时不发 SDK 命令；保护删除失败时不导入历史。
7. 端到端测试必须走用户可达流程，禁止在测试中额外手动断连或改 guard 来填补生产缺口。
8. 旧无编号未知状态不能静默升级为新请求，新增能力不能作为遗留证据。
9. 扫描、缓存恢复列表及权限返回必须再次确认本轮仍可搜索；旧查询返回 0 不代表新连接后确实没有设备。正常断线保留记忆目标仍允许手动搜索。
10. 非活动 SDK 的安装级重连地址与 App 账号绑定是不同数据。换通道只取消旧 SDK 会话和安装级自动重连，不得用解绑、清数据或恢复出厂代替退出；同通道自然恢复仍保留。
