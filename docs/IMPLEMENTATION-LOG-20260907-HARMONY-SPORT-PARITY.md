# 鸿蒙运动与记录完整闭环

## 结论

鸿蒙端已从“只同步历史”补齐为运动模式选择、手表启停、实时计时、前台轨迹、结束保护、本机加密保存、记录列表和详情页。

本轮只连接 W9S，没有切换 ET488。当前 W9S 实报 3 个运动模式、类型 3、无实时控制扩展，因此显示跑步、步行、骑行，不显示暂停和未确认的徒步入口。

## 根因与修复

| 项目 | 修改前 | 修改后 |
| --- | --- | --- |
| 能力判断 | 页面只有历史同步；首次实现又把实时控制扩展误作唯一开关 | 按官方示例先读取 `sportModeCount`，再按模式数量和类型开放真实入口 |
| 协议 | 未接运动控制 | 普通设备使用模式开关协议；明确支持实时控制的设备使用开始、暂停、继续、停止协议 |
| 状态 | 无统一运动会话 | 增加开始、运行、暂停、结束中、完成、错误状态和连接代次保护 |
| 数据 | 无实时运动卡和轨迹 | 优先显示手表时长、距离、热量和心率；手机仅记录前台真实位置 |
| 记录 | 只读手表历史 | App 完成的运动按账号和设备写入加密库，列表与详情可离线查看 |
| 安全 | 离开页面、换号和断连没有运动保护 | 运动中拦截其他手表命令；退出先确认；迟到指令不能覆盖新账号或新设备 |

官方鸿蒙 SDK 自带运动页面以 `sportModeCount > 0` 作为运动能力入口，并分别提供模式控制、实时控制和历史读取。实现依据为 [Veepoo HarmonyOS SDK](https://github.com/HBandSDK/HarmonyOS_BLE_SDK)。

## 自动化与构建

- 新增能力映射、模式数限制、协议值、轨迹去噪、距离、空状态、保存一次和命令串行测试。
- UTC 完整测试 428/428；Asia/Shanghai 完整测试 428/428；失败、跳过均为 0。
- Debug 与 Release 各 33 个构建任务成功；官方 `verify-app` 均通过代码、摘要和权限签名验证。
- 版本提升为 0.1.4（8）；Release 仍使用已登记设备的开发 Profile，不等于 AppGallery 正式发行签名。

## W9S 真机结果

- 华为 nova 14 覆盖安装后登录、设备绑定和旧本机数据保留；当前连接仍为 W9S。
- W9S 实报 `sportModeCount=3`、`sportModeType=3`、`daSportControl=0`，页面只展示 3 个真实模式。
- 户外跑步开始指令成功，手机端进入实时计时；结束指令成功，手表与 App 均退出运动状态。
- 生成一条 51 秒 App 运动记录；重启新版后记录仍在，详情页显示时长、来源和无轨迹说明。
- 室内静止测试没有形成有效移动轨迹，客户端未补造路线、距离、热量或心率。

## 保留边界

- 只实测了 W9S 的跑步启停；步行、骑行仍需实际户外样本逐项核对手表端名称和统计值。
- W9S 不支持实时控制扩展，所以不显示暂停/继续；该入口仅在设备明确上报后出现。
- 后台持续定位不在本轮范围；App 在前台且获准定位时才记录轨迹。
- ET488、W9 及 Yuc 鸿蒙运动控制未在本轮验证；Yuc 在缺少原生鸿蒙 SDK 时仍只发现和识别。
