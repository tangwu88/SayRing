## 正常页面实测

1. 设备页实际显示 `SD-RING-R7 Ultra`、已连接、同步按钮可用；没有将上轮 R8 结果当作本轮结果。
2. 手动同步前，“我的”页显示健康记录9条。
3. 正常结束并重新启动本 App，保留账号和原绑定：约5.3秒设备页等待原目标靠近，约7.8秒同一 R7 Ultra 恢复已连接。观察窗口约70秒内没有点击重连/同步，也没有观察到自动历史同步状态；窗口结束后仍显示9条。
4. 使用真实同步按钮进行一次对照：约2.5秒观察到读取活动与睡眠状态，约33.0秒恢复按钮，并明确提示“未收到戒指的完整数据，请稍后重试”。可见忙状态约30.6秒，连接保持。
5. 手动轮之后健康记录显示12条。正常首页的可见活动与睡眠内容和手动前一致；没有据此宣称活动或睡眠已经更新。显示记录数受当前戒指/发布门禁/日期等投影影响，且可能同时接收被动或云端记录，不能仅凭9→12断言三条全部由本次历史同步产生，更不能视为完整入库/去重证明。

本轮无睡眠记录本身不作为错误证据，也不把缺失项补零。可确认的失败证据是：正常重开后没有自动发起历史读取，以及手动轮收到明确的不完整数据提示。

## 源码对应与结论

- `AppController.connectDevice` 中 CoolWear 路径明确优先保持测量可用，连接后显示“可手动同步历史数据”，没有调用 `_syncInitialDeviceData`；`_restoreReconnectedDevice` 对同一 SDK 使用相同策略。该策略最早来自`452ab89f`，当前 R7 Ultra 实际走此路径；不能套用 QRing R8 的自动历史读取结果。
- Android `CoolWearRingBridge.startSync` 开启厂商数据接收并调用 `sendAsynInfo`，等待真实 SDK 流及完成回执；`CoolWearSyncWindow` 为30秒无新包/最多90秒有界等待。约33秒的页面结果与等待终态相符，但单凭时间不能判断厂商根因。
- 原 SDK 复核已记录 `sendAsynInfo` / `sendGetMixInfo` 存在设置写入副作用，见 `SAY-RING-LUCKRING-SDK-REVIEW-20261104.md`。本轮不擅自替换同步命令、重复写入设置或把超时当成功。仍须核对历史请求、回包、完成确认和安全触发时机。

**结论：当前正式1235上的R7 Ultra自动历史同步未实现，手动历史读取也未通过完整性确认，不能交付“正常同步”的验收结论。** 确实观察到显示记录数增加，但来源和完整性尚未逐条核验。两项问题保持OPEN；未修复、未重新打包，不把“已连接”或按钮恢复写成同步成功。
