## 已修复的 P1 问题

原始 SDK 的 `sendAsynInfo → sendAynInfoDetail → sendMixInfo` 会写入缓存资料、目标、时间／显示格式、来电／消息开关、类别和配对完成项。`sendGetMixInfo` 也有设置写入。原接入在连接握手、历史读取、提醒读取、电量刷新、能力补读和监测设置读取使用了这类方法；详见 [原始 SDK 复核](SAY-RING-LUCKRING-SDK-REVIEW-20261104.md)。

本轮修改：

1. 新增 `CoolWearReadRequests`，只接受封闭枚举中的原厂公开类型，构造全新的 `CEDevData`、`CMD_TYPE_REQUEST=3`、空载荷查询。设备信息、电量、混合信息、能力、时间、久坐／饮水与自动监测查询不再借用混合写入方法。
2. `CoolWearRingBridge` 六处普通读取改为上述查询，发送前确认当前连接和 SDK 代理目标一致。历史读取只保留明确的数据上报通道开关，再请求数据；不回写用户资料、目标、提醒、监测设置或配对完成状态。
3. 提醒／监测读取未启动或失败时释放对应等待，不伪造读回结果；可选电量或能力补读失败不拆除正常连接。普通重连仍保留绑定，不通过 `unbindDevice` 释放连接。
4. 校时与读取分开：只有本轮真实返回时间显示格式后，才可能发送每条连接至多一次的独立校时。未返回格式、格式无效或正在测量／同步／读取设置时跳过，不从安装缓存猜测格式，不重发整个设置包。当前实物观察窗口没有返回 type104，不能宣称已完成校时。
5. iOS 仅增加 DEBUG 下、当前 HRV 会话中的帧头类型／长度观察，继续区分“传输没有结果头”和“解析没有有效样本”。不打印健康数值、原始包或账号标识；Profile 不包含该观察标记，不改变正式测量协议。

**不要用另一条混合写入方法替换被禁方法，也不要为得到 ACK 而补默认开关。** AAR 的配对完成接收处理还能触发 `sendSynDevData`，因此源码名称检查之外，必须观察最终 SDK 队列和实际发送结果；不能盲目补发 type120。当前没有证据证明 type120 是 R7 Ultra／869 固件无有效 HRV 的根因。
