- P1：前台定时读取到真实待处理邀请，写入本地收件箱并提醒；紧接着旧服务端未读接口返回 0，Controller 将全部非设备事件置为已读，新关爱请求红点随即消失。
- 预期：聚合计数不等于某个邀请的已读确认。关爱事件必须保留到明确已读、真实处理，或此前已知待处理项在成功刷新后撤销；切换账号不能跨账号清除或显示。
- P2：原前台轮询已有收件箱和本地系统通知，却没有全局关爱横幅。复用既有健康提醒所在的 App 全局提示层；不新增另一套系统通知调用。

## 修改

- `lib/services/app_controller.dart`：远端 0 不再清除关爱事件；远端聚合数与本机已知未读取较大值，避免吞掉本地事件或直接相加重复计算。聚合接口不返回事件 ID，因此这只是安全下界，精确跨端合并仍需服务端稳定通知契约。
- 邀请明确返回 `examine_status=1/2` 时，可在重新登录后核销此前持久化未读；缺失/未知状态不伪判为已处理。保留既有本次会话待处理变为移除的撤销处理。
- 新关爱事件在前台生成通用横幅；关闭只收起横幅，查看才标记该消息已读并进入真实邀请页，绝不自动接受或授权。健康预警优先显示，两种横幅不重叠。
- 横幅使用同一规范化 `care-invitation-{entityId}` 去重；后续远程 event ID 不同但实体相同的重投，不新增记录、横幅或本地系统通知。
- 横幅在退出、切换账号和离开前台时清空；读取操作携带账号代次，旧读取完成后不能用新账号发送已读请求或续跳旧邀请。
- `lib/app.dart`：提示只写“收到新的关爱请求”，提供查看与无障碍关闭按钮；不显示账号、健康值或接口逻辑。必要更新门禁未结束时不显示关爱横幅。

## 边界与后续

- 这不是后台即时推送验收；前台轮询仍为 30 秒及原退避，进程结束不轮询。客户端已有本地提醒与 SDK/系统自动显示的远程通知若都投递，同一实体的跨通道替换还需服务端/平台通知 ID 协同，不能承诺仅本次改动就做到系统级合并。
