## Implementation

- `GlobalEnvironment.storageNamespace` is the SHA-256 digest of normalized configured origin plus the fixed international API prefix. Storage accepts only a 64-character lowercase hex digest; tests inject explicit non-secret digests.
- Global session, consent, warning settings, cart, pending push unregister, migration marker and SQLCipher encryption key use `saydian.global.env.<digest>`. Global health filenames include the same digest; constructor rejects a secure-vault/database namespace mismatch.
- The database already contains health, sports, warnings, metadata/cursors and notification inbox; separate files therefore isolate all these tables without changing data values or per-account owner logic.
- Old `saydian.global.*` keys, the old `saydian_global_health_v1.db` and its encryption key are not read, rewritten, renamed, deleted or automatically migrated. New databases never adopt `legacy-unscoped` records. Existing domestic migration behavior and memory-vault tests remain unchanged.
- JPush installation ID and permission explanation are scoped by environment. Old provider IDs are not used to unregister another environment's account. Server/provider transport isolation remains a separate acceptance requirement.
- Saved transport and exact native identifier are stored atomically in a scoped binding; Yucheng's saved fields are also scoped. Production recovery never blindly invokes the SDK's installation-wide saved-target restore. It scans only the bound SDK and connects only an exact saved native identifier; absent targets or same-name devices are not substituted. Generic bridge callers retain the existing compatibility recovery behavior.
- Cancelling automatic restoration via the controller's `stopScan` invalidates the restore generation before stopping native scans. A partial scan result or late callback cannot restart the target after cancellation; the saved target remains available for a later explicit retry.
- No native SDK preferences, user handshakes, real watch settings, account data or backend database were changed by this subtask. First installation of the scoped build intentionally requires signing in and explicitly selecting the watch again; old data remains recoverable in its original files/keys, not automatically assigned to the new account.

### 2026-09-10 review follow-up: bounded recovery and late native completion

- Independent review identified two P1 gaps before packaging: cancellation during a pending native connect discarded the result without closing that old native connection; a native stop-scan callback that never completed could leave recovery and account transition awaiting indefinitely.
- Added active connection ownership separate from cancellation generation. A canceled recovery waits for its native connect to settle and disconnects only its own generation; an already newer explicit connection is never disconnected by old cleanup.
- Recovery scan/connect/disconnect use the existing 30-second operation limit; stop-scan uses the controller's existing 3-second grace. A connect timeout registers bounded late-completion cleanup and does not mark the session active. No next SDK command is started by that recovery after timeout. If the vendor never completes, the Dart operation returns failure rather than hanging; actual radio recovery remains a native/device acceptance item.
- Added five regressions: pending connect canceled then native success; missing stop-scan callback; scan timeout with late results; connect timeout followed by late success; old late success after a new explicit connection. Cancellation and timeout tests do not assume a Dart timeout cancels native work.
- `dart format lib/services/wearable_routing.dart test/global_wearable_restore_test.dart`: 2 files formatted. `flutter test --no-pub --reporter expanded test/global_wearable_restore_test.dart test/wearable_routing_test.dart test/wearable_bootstrap_test.dart test/app_controller_wearable_restore_race_test.dart test/app_controller_account_wearable_test.dart`: **35/35 passed**, including all 11 exact-recovery tests. Scoped analyze and diff checks were then executed; see subsequent corrections if any.
- Follow-up review found that a single active-generation field could strand a late Veepoo connection after selecting Yucheng, and that timing out the cleanup future itself released ownership too early. Replaced that intermediate approach with per-transport ownership plus a per-transport **original-future drain barrier**. The caller's 30-second wait is bounded, but the underlying connect/required-disconnect chain stays tracked until it actually settles. A new connection to that same SDK gets an ordinary retryable `RECOVERY_PENDING`; the other SDK remains available. Thus no timeout is treated as proof the native channel is idle.
- Cross-SDK late completion now disconnects only the retired source, leaving the new active SDK untouched. Canceled/retired callbacks are suppressed while native work drains, including a late `reconnected` event, so they cannot revive the old UI session.
- Replaced the intermediate permissive same-SDK test with a refusal-until-drained test; added cross-SDK cleanup and pending-cleanup-after-timeout cases. The final same command above passes **37/37**, including 13 exact-recovery tests. Final scoped analyze: **No issues found**. No failed native operation or missing callback was converted into a successful connection result.
