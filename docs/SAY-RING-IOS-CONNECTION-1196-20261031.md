# 2026-10-31 XR 连接稳定性与重连速度 1196

用户要求：戒指在身边、有电时尽量保持连接，连接速度尽可能快。本轮继续使用 iPhone XR 与原 SD_RING_R8，保留原账号、绑定、设置、照片和健康数据。以已同步并 fetch 核对的 `8ac4943` 为基线，不把上一轮手势回读或一次重连成功当作长期连接稳定性的证据。

本轮已完成1196正常开发签名构建、XR保数据覆盖安装及同一R8的前后对照。重连中位数从12.62秒降为2.48秒；新版前台5分钟和后台2分钟返回均保持连接。测试时Flutter附加，结果不代表整夜后台、系统回收或所有型号永不断连。完整边界和保留风险见下文。

## 问题、原因与最终范围

1. 已经由当前账号确认的同一台戒指，用户点击重新连接时仍可能重复经过准备/扫描或配置恢复目标。新增精确目标的手动恢复入口，复用当前环境、稳定账号 owner、原生标识和已有有效恢复上下文，减少不必要的准备。只有实际厂商握手完成才能成为已连接；发起恢复请求不是连接成功。名字不单独授权恢复，另一账号、另一目标、旧代次和无有效记录仍拒绝。
2. native 连接失败先上报 `Disconnected`，再回调 `didFailConnected`。原 bridge 已在第一个回调中清除 `recoveryConnecting`，导致后一个失败回调跳过 2 秒冷却。现在在清理前保存“握手中且非主动取消”的条件，再保留失败冷却；正常已连接会话的意外掉线仍在下一轮主队列立即恢复，不增加固定等待。
3. 详情读取期间，将会争用 SDK 命令通道的公共功能请求保持为忙，包括健康提醒振动；不会为了立即发出另一个命令而并发操作 SDK。现有停止/清理路径、相机退出、代次和取消屏障继续保留。
4. 增加仅 Debug 使用的连接阶段记录，区分请求、无线连接、SDK 注册、能力、资料、电量、固件和准备完成。沿用本机有界缓存日志，不记录账号、设备标识或健康原始数据；不把这些内容放到用户页面。

主要涉及 `QRingWearableBridge.m`、Dart 的 bridge 接口、路由和控制器，沿用设备页现有重新连接入口。新增原生恢复回归夹具和相应控制器/路由测试。没有改变数据算法、戒指协议路由、首次绑定清空规则、账号归属或恢复目标范围；没有卸载、解绑或恢复出厂。

## 撤回的候选与仍未解决的风险

1. 曾评估将首次连接的固件读取移到显式“关于设备/固件”操作，并区分 UI 回复和 SDK 命令占用。候选回归通过不代表产品范围可接受：HRV/皮温个人参考依赖精确设备和实际固件，改变固件首读会影响已有参考的可用性。因此本轮已撤回固件拆分，保留首次读取及原始 33 条性能测试，仅增加 trace stub。此前拆分候选的 68 条断言不计入最终版本证据。
2. 原详情方法 10 秒等待结束时会调用后续流程，但底层固件 SDK 可能仍占用命令通道。该问题本轮没有完整修复。不能以详情超时主动拆掉健康蓝牙连接，也不能简单缩短/延长超时或并发发下一条 SDK 命令；后续需独立区分 UI 回复、SDK 实际结束和后续握手启动，并联动核验各层超时及精确固件参考。
3. 蓝牙关闭或重置后，如果仅发生状态变化而没有 `didDisconnect` 回调，合成序列仍显示恢复 pending 未重新挂接。测试确认原 owner/目标和绑定没有被清除，但没有证明恢复成功，也没有把这一合成序列当作 XR 的实际故障。本轮未推测触发解绑或扩大恢复目标。
4. iOS 前后台切换没有发现主动断开健康连接的代码；后台模式和系统状态恢复已有配置。此项源码检查不等于锁屏/后台/系统回收后的真机验收，更不保证任何情况下持续在线。
