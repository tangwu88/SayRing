# Android R7 Ultra 自动历史同步修复候选与验收记录

## 范围与当前结论

用户要求每次重连自动同步戒指实际历史，修复未收齐的原因，不能通过隐藏提示或补零交付。当前戒指为 R7 Ultra；用户确认心率自动监测间隔为10分钟，原厂 App 曾有历史。保留账号、绑定、手机/云端及戒指记录，不解绑、不重置、不清库、不改变监测参数。

本轮基线为 `f60f8f0256e1a21a01117102e6231fe38f151970`，独立仓库 `tangwu88/SayRing`、分支 `codex/integrate-latest-20261031`。开始时工作树干净且 fetch 成功，远端当前分支同 SHA；此前的原厂 SDK 复核和1235实测记录均已阅读。没有修改服务端、地图、商城、下载配置或生产凭据。

**这是修复候选，尚未证明这只 R7U 的全部历史已正常回读。** 在1236/1237实测中收到当前活动，历史查询多数只有零字节回复，61没有实际历史；不将零字节当成无历史，不将命令 ACK 当成同步完成。需要在佩戴至少一个自动监测周期后，用最终代码的真实安装包完成重新连接与自动回读，才能关闭问题。

## 已确认问题与代码

1. `AppController` 原 CoolWear 分支在初次握手及恢复握手后均只提供手动历史同步。Android 两处改为调用现有自动同步入口；iOS 原范围、QRing 窗口/检查点和所有权/初始化保护保持原约束。重置前后不能在旧握手导入缓存。
2. 原 Android `startSync` 仅请求混合信息并等待超时，没有完整历史完成依据。按本轮实际原厂 LuckRing APK 的 `requestDataSync` 对照，只读 DEV_SYNC(3/9)、当前活动(3/4)，再请求实际能力相关历史类型。使用现有公开 `CEBluetoothProxyBase.sendData(CEDevData)`，不修改 SDK 二进制、不把混合设置响应当成历史结束。
3. `sendAsynInfo` 与 `sendGetMixInfo` 均会夹带设置写入，故不再在本次历史请求中使用。原有连接握手/显式设置处仍有独立旧调用，**不能宣称整个 App 已消除该 SDK 复核中的设置写入风险**。
4. 新增 `SayRingHistoryObserver`，在已安装 SDK 的原解析器之后追加观察器；不替换原监听、不使用生产反射。接受 SDK 解码数据帧 -10001/-10002，排除命令 ACK(-99)。使用剩余条数、包内条数和唯一记录严格记账，重复/缺中包/畸形包不报完整；只有明确三字节空终包才能证明无数据。
5. SDK 可能在 Flutter 账号/握手就绪前发送并确认历史。原生现按连接与目标缓存有效映射记录，并在显式读取中重放；历史回调不再因设备详情尚未就绪直接丢弃。同步结束也要等待原 SDK 公共监听的最后一轮映射排队执行。
6. Flutter 在本地加密数据库写入成功后才确认不透明的记录版本凭据；原生仅释放同一版本缓存。保存失败、旧版本迟到、换目标/账号等不能释放新记录。凭据属于本地传输元数据，不加入健康值、服务端字段或日志。超时仍返回已收记录及不完整状态，保存有效部分后业务返回 false，不改成成功。

主要源码：`CoolWearRingBridge.java`、`CoolWearHistoryBatch.java`、SDK包内观察适配器；Flutter同步结果/桥接/路由和`AppController`。测试覆盖真实 AAR 解析器、生产同步方法时序、保存确认及重连/初始化回归；CI Android 步骤加入新 AAR 测试。
