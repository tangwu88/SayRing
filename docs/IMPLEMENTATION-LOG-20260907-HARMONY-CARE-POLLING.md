## 数据与通知安全

- 本地只保存邀请 ID、首次收到时间、已读状态及最近是否待处理；不保存邀请人姓名、手机号、令牌或健康值。消息最多保留 200 条，已提醒 ID 保留，避免旧邀请再次弹出。
- 初次发现的待处理邀请会进入本地收件箱，成功持久化后才产生简短前台提示和系统通知；通知失败不会假装保存失败或重复弹出。
- 接口读取失败不会清空旧记录，也不生成空列表替代真实结果；仅明确返回已接受/已拒绝的邀请会更新为已处理。缺席、未知或撤销未有明确字段时不猜状态。进入邀请页面和执行接受/拒绝前仍查询真实服务端状态。
- 本地通知只显示“新的关爱邀请 / 请打开赛电查看并选择是否接受”。点击中保留账号范围，仅允许 `care-invitations`；旧账号通知不能将新账号带入旧邀请操作。
- 本地先到、远程后到时按同一邀请实体合并，不重复本地横幅、消息和系统通知；远程先到时先查询真实邀请，再保存本地消息，不再次发布本地通知。

## 系统跨通道去重仍需服务端配合

- 已核对当前 DevEco SDK 的 `notificationRequest.d.ts`：API 12 `appMessageId` 支持本地/云同 key 去重，窗口为 24 小时，重启后失效。
- 本地设置 `appMessageId = saydian.care.<接收账号ID>.<邀请ID>`，且 `isAlertOnce=true`。服务端鸿蒙推送应使用相同业务 key，并保留稳定 event_id / entity_id。
- 极光 `onArrivedMessage` 在系统展示后回调。客户端会取消对应旧本地通知，但不能保证已经弹出的远程系统横幅被撤回；未配置同 key 的远程推送不能宣称系统级去重已验收。
- 服务端消息若没有 `entity_id` 或 `invitation_id`，不能凭文字或列表位置猜测与本地哪条邀请相同；该类旧消息保留，跨源精确去重需要服务端补稳定业务标识。
